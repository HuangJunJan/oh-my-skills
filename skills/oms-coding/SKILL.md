# 通用编码规范 | General Coding Conventions

本 skill 是 OhMySkills 的**通用编码规范层**（language-agnostic / stack-agnostic）。任何代码改动都触发，与领域 skill（`oms-fe-coding` / 未来 `oms-be-coding` 等）叠加生效。冲突时领域 skill 的具体规则优先；本 skill 未覆盖的领域细节由领域 skill 补充。元层规则（优先级 / 平台基线 / 工具能力 / 不确定不假设 / skill 间引用）见 `$oms-meta`。

本 skill 管「代码怎么改」：写之前查什么、写的时候守什么、变更范围多大、什么操作不能做、怎么验证、怎么交付。对话风格交给 `$oms-qa`。

## A. 编码前 | Before Coding

- **复用优先**（reuse first）：动手前先读相邻模块、同业务域、已有 hook/工具/抽象。能复用就不新增包装层、不写新转换、不基于猜测加工。
- **一致性优先**（consistency first）：新代码风格、命名、目录结构、接口形态必须对齐项目已有惯例。看不出惯例就先读 3~5 个同类实现再下笔。
- **最小改动**（minimal change）：只动需求覆盖的范围；不顺手重命名、不顺手重排、不顺手「优化」无关代码。
- **简单实现优先**（simple solution first）：避免过早抽象、过度设计、提前为「可能的未来需求」预留扩展点。需要时再抽。
- **接口字段为唯一事实源**（single source of truth）：接口字段以后端真实返回为唯一事实源，不依赖印象、过时文档、缓存记忆。先看接口实际响应再写类型。
- **ID 类字段统一 `string`**：无论后端定义为何类型（int / long / uuid），前端 / 调用方统一 `string` 处理，避免精度丢失与隐式转换。

## B. 编码中 | While Coding

- **命名简洁且语义准确**（concise and semantic naming）：文件夹、文件名、变量、方法、class 名都要短而准。避免堆砌词（`UserManagerHelperServiceImpl`）、避免无效前后缀（`xxxUtilHelper`）、避免重复语义。
- **清理死代码**：默认删除无作用的代码、空配置、注释掉的旧实现、「可能以后用」的分支、重复映射、重复兜底。不留 dead code / no-op config。
- **注释「必要且够用」**：
  - 方法默认写注释（极简单的赋值/转发可豁免）。
  - 重点说**为什么这样做**、边界/约束、关键变量含义、必要分支理由。不写翻译式注释（"increment i by 1"）、不写显而易见的逐行注释。
  - 方法注释优先 **JSDoc** / docstring；整体优先块级注释；避免空洞注释。
- **类型定义统一收敛**：同一业务模块的 TS 类型集中到模块根的 `type.ts`（或语言对应的等价位置），页面与子组件通过 `import type` 复用。避免同结构类型在多处重复定义（shared module types）。
- **不做类型体操**：TypeScript 类型保持精简、可读；不为了「类型炫技」写难懂的条件类型/映射类型。

## C. 变更安全 | Change Safety

- **默认只做局部修改**：读取、搜索、列目录、看 diff、改现有文件、跑最小验证。不做全量格式化、全量重排、大范围批量替换。
- **能改现有文件就不新增文件**；确需新增时优先放入现有合适目录，不在仓库根目录直接新增（包括 log、临时脚本、调试输出、一次性说明文档）。
- **未经明确要求不重命名 / 不移动 / 不调整目录层级**。
- **不修无关问题**（out of scope）：发现可以提示给用户，但不顺手扩改。
- **存量报错与当前任务无关**：仓库已有的全局 `type-check`、lint、test 存量报错一律视为范围外，不处理也不作为收尾事项。
- **不引入新依赖**：未经明确要求不新增 UI 库、状态管理方案、网络请求封装、目录结构。
- **禁兼容旧逻辑**（no legacy compatibility）：除非用户明确要求，不兼容旧字段 / 历史分支 / 双轨口径；不写去重 / 判空 / 重组映射等修正逻辑兜底已删除的旧字段。

## D. 敏感操作 | Sensitive Operations

- **`.env*` / 密钥 / 证书默认只读**。确需修改要用户明确要求，且交付时说明原因与影响范围。
- **禁破坏性命令**（destructive commands）：
  - `rm -rf`、`Remove-Item -Recurse -Force`、`del /s /q`
  - `git clean -fd`、`git reset --hard`、`git checkout .`、`git restore .`
  - 任何「清空目录」「批量覆盖」「回滚历史」类操作
  - 上述操作必须经用户明确确认后才能执行。
- **不主动删除文件或目录**。
- **提交前查敏感信息**：任何 commit / push 前自查是否含密钥、令牌、凭证、内部敏感地址、生产数据库连接串等。发现就停止，先与用户确认。
- 工具能力前置确认 / 浏览器无痕等元层约束见 `$oms-meta` 第 3 条。

## E. 验证策略 | Validation Strategy

（默认局部验证原则见 `$oms-meta` 第 5 条；本节展开具体细则）

- **不跑生产构建作为验证**：`pnpm run build` / `vite build` / `npm run release` 一类命令默认不执行。优先选择类型检查、lint、单测、局部走查这类更快的校验方式。确需构建时先说明原因征得同意。
- **接口/数据流改动核对链路**：改了接口参数、字段映射、数据流时，至少核对一次「请求参数 → 接口返回 → 页面绑定」三段链路是否对齐。
- **类型检查、lint、已有测试是否跑，按任务影响范围独立判断**。一行注释改动跑全量 type-check 是过度。
- **替代验证**（fallback verification）：无法跑自动化验证时（环境缺失、需要真机、需要后端联调），说明替代方案（代码走查、关键断言、人工验证步骤说明）。

## F. 交付报告 | Handoff Report

交付时报告必须包含：

1. **改动文件**：列出所有新增/修改/删除的文件，**用绝对路径或仓库相对路径**，不写「我改了几个文件」这种模糊表述。
2. **核心原因**：每组改动一句话说明「为什么这样改」（不是「改了什么」——文件 diff 已经说明改了什么）。
3. **验证方式**：说清楚跑了什么命令、看到什么输出。没做自动化验证时说明替代方案。
4. **未做的事**：明确列出本次没做、留给用户或后续任务的事项。避免用户后来发现「以为做了其实没做」。
5. **风险与边界**：改动可能影响的相邻模块、需要用户复测的场景、已知的限制。

## 反 anti-patterns

- ❌ 写新工具函数前不搜 `src/utils/` 看有没有现成的。
- ❌ 改个 bug 顺手「重构」无关的 3 个文件。
- ❌ 在仓库根目录新增 `test.js` / `debug.log` / `notes.txt`。
- ❌ 改了一个字段映射就跑 `pnpm run build` 验证。
- ❌ 交付时只说「完成了」，不列改了哪些文件、跑了什么验证。
- ❌ 看到 `.env` 里有占位符就主动改成真实值。
- ❌ 为「未来可能的需求」预先加一个抽象层。
- ❌ 改字段映射时基于印象写类型，不看接口实际响应。
- ❌ 为兼容已删除的旧字段保留判空 / 兜底逻辑。
