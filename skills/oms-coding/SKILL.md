# 通用编码执行规范 | General Coding Execution

本 skill 是通用编码层，任何代码改动都触发。前端见 `$oms-fe-coding`，后端见 `$oms-be-coding`，对话见 `$oms-qa`，元规则见 `$oms-meta`。领域 skill 的具体规则优先于本 skill 的通用规则。

## 1. 工作方式

- **先读再改**：读取相关代码、相邻实现、测试、类型、接口契约和已有工具函数。优先用 `rg` / `rg --files`。
- **少问多查**：能从代码、文档、配置、日志、测试确认的事实，不反问用户。
- **先定成功标准**：明确本次完成的可验证标志，例如复现 bug、目标测试通过、接口链路对齐、UI 状态可见。
- **多步先列计划**：超过 2 步时给“步骤 -> 验证”清单；每步完成后按清单推进。
- **局部改动**：只改需求覆盖范围，不顺手格式化、重命名、重排、升级依赖、调整目录或修无关问题。
- **既有契约优先**：维护老项目时先遵循现有公开契约、目录、样式和流程；要改变历史行为必须说明影响面、迁移策略和调用方同步。

## 2. 调试优先

- **先定位根因**：修 bug 前先找到失败点、触发条件、数据流和责任边界；能写复现测试/样例就先写。
- **让失败可见**：错误必须通过异常、返回值、日志或测试暴露。禁止空 `catch`、`except: pass`、吞错误、假成功、模拟成功。
- **禁止静默兜底**：不要为“看起来能跑”添加 fallback、默认值、try-catch、判空、防御分支或旧字段兼容。
- **允许显式业务默认值**：有明确业务语义的默认值、空态和降级可以存在，但必须命名清楚、可观测、可测试，不能掩盖错误。
- **边界才防御**：用户输入、外部 API、跨服务调用、文件/网络/数据库等不可信边界要显式校验；可信内部调用不要过度防御。
- **必要降级要显式**：安全、权限、外部依赖降级必须说明触发条件、日志/指标、关闭方式和行为影响。

## 3. 修复策略

- **根因修复**：修问题本身，不绕过症状。若过度 gate / mode / 兼容层导致问题，优先删除它们。
- **复用优先**：复用已有函数、hook、middleware、schema、类型、组件和项目惯例；不要基于猜测新建一套。
- **删除自己产生的孤儿**：本次改动造成的未引用代码、导入、变量、类型、配置同步清理。历史遗留死代码只提示，不顺手删。
- **拒绝 mode 堆砌**：不要用 `bool` / `enum` / 字符串 `mode` / options bag 让一个函数承载多套本质不同的业务流程。
- **结构性问题结构性修**：共享校验、权限、API 契约、数据迁移、状态同步、安全、跨模块重复 bug，要修公共边界。

## 4. 代码质量

- **简单优先**：没有真实复杂度就不抽象、不加配置项、不引入策略模式或插件钩子。
- **命名准确**：名称短而语义完整，避免 `ManagerHelperServiceImpl`、`xxxUtilHelper`、重复前后缀和模糊词。
- **函数清晰**：短函数、浅嵌套、guard clause、命名常量、清楚的输入输出。业务逻辑不要绑定具体实现。
- **类型收敛**：同业务类型 / schema 放到统一位置复用，不在调用方重复定义；类型和泛型以可读性优先。
- **注释克制**：注释解释意图、边界、取舍和非显然原因，不翻译代码。修改行为时删除废弃注释和死分支。
- **必要注释**：遇到非显然业务规则、兼容历史行为、并发 / 缓存 / 事务边界、安全或性能取舍、数据格式转换、协议 / 接口怪癖、复杂正则或解析逻辑时，写简短注释说明原因和约束。
- **安全基本线**：外部输入在边界校验；数据库访问用参数化查询；不硬编码密钥、token、生产地址或真实凭证。
- **依赖克制**：不新增依赖，除非已有能力无法满足且收益明确。新增或升级依赖前先查项目已有依赖、标准库、框架内置能力和工具函数；必须改依赖时同步 lockfile，并说明原因、替代方案、影响范围和回滚方式。

## 5. 敏感边界

- 不动用户改动；不要 revert、覆盖或整理不是本次任务产生的变更。
- 不主动删除文件/目录；确需删除时先确认，且只删明确目标。
- 破坏性命令必须用户明确同意：`git reset --hard`、`git clean -fd`、`git checkout .`、`git restore .`、`rm -rf`、`Remove-Item -Recurse -Force`。
- `.env*` / 密钥 / 证书默认只读，除非用户明确要求。
- 不主动执行 `git commit` / `git push` / `git amend` / `git rebase`，除非用户明确要求。
- `build` / `package` / `release` / `publish` / 生产部署命令默认不作为验证手段；确需执行先说明原因并确认。

## 6. 验证

- 按影响范围验证：目标测试、相关 lint/type-check、局部脚本、最小 smoke test 优先。
- 测试验证行为和契约，不绑定旧实现细节；旧测试与正确设计冲突时更新测试，不保留错误兼容逻辑。
- 不手改生成文件，除非项目明确要求；应修改源文件后运行生成命令。lockfile、schema 生成物、API client、snapshot、migration 等变更必须能追溯到源改动。
- 更新 snapshot 前必须确认行为变化是期望结果，不用更新快照掩盖 bug。
- 改接口字段、参数、权限、状态或数据流时，核对“上游输入 -> 契约 -> 下游消费”。
- 验证失败不要堆补丁，回到根因；无法验证时说明阻塞、替代检查和剩余风险。

## 7. 交付前自检

- 每一行修改都能对应用户请求或成功标准。
- 没有隐藏 fallback、吞错误、假成功、旧字段兼容、无意义防御代码。
- 没有重复逻辑、mode 堆砌、过早抽象、无关重构、新依赖。
- 自己造成的孤儿已清理，历史遗留问题未越界修改。
- 已查看本次 diff，确认没有无关格式化、调试代码、临时文件、密钥、权限位、行尾噪音或混入用户既有改动。
- 相关验证已运行，或已说明无法运行的原因和替代证据。

## 8. 交付报告

最终报告简洁包含：改动文件、为什么这样改、验证命令与结果、未做事项、风险边界、需要用户复测的场景。

## 反 anti-patterns

- 避免：没读相关代码、相邻实现、测试和既有工具函数就动手改。
- 避免：为“看起来能跑”加空 catch、默认值、判空或防御分支，掩盖真实错误。
- 避免：顺手格式化、重命名、重排、升级依赖或修无关问题。
- 避免：用 bool / enum / 字符串 mode / options bag 让一个函数承载多套本质不同的业务流程。
- 避免：新建一套已有的函数、类型、组件或项目惯例，不复用。
- 避免：把“没报错”当成功，不对应明确可验证标准。
- 避免：留下自己产生的孤儿代码，或顺手删历史遗留死代码。
