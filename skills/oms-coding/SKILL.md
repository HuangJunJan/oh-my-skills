# 通用编码规范 | General Coding Conventions

本 skill 是 OhMySkills 的**通用编码规范层**（language-agnostic / stack-agnostic）。任何代码改动都触发，与领域 skill（`oms-fe-coding` / 未来 `oms-be-coding` 等）叠加生效。冲突时领域 skill 的具体规则优先；本 skill 未覆盖的领域细节由领域 skill 补充。元层规则（优先级 / 平台基线 / 工具能力 / 不确定不假设 / skill 间引用）见 `$oms-meta`。

本 skill 管「代码怎么改」：写之前查什么、写的时候守什么、变更范围多大、什么操作不能做、怎么验证、怎么交付。对话风格交给 `$oms-qa`。

## A. 编码前 | Before Coding

- **复用优先**（reuse first）：动手前先读相邻模块、同业务域、已有的工具 / 抽象 / 复用单元（函数、中间件、hook、helper、装饰器等）。能复用就不新增包装层、不写新转换、不基于猜测加工。
- **一致性优先**（consistency first）：新代码风格、命名、目录结构、接口形态必须对齐项目已有惯例。看不出惯例就先读 3~5 个同类实现再下笔。
- **最小改动**（minimal change）：只动需求覆盖的范围；不顺手重命名、不顺手重排、不顺手「优化」无关代码。
- **简单实现优先**（simple solution first）：避免过早抽象、过度设计、提前为「可能的未来需求」预留扩展点，避免未被要求的灵活性 / 可配置性（如配置项、策略模式、插件钩子、可替换实现）。需要时再抽。
- **不默默选择 / 困惑就停**（no silent guess）：需求或代码意图有歧义时，不默默挑一种解释埋头实现。列 2~3 种合理解释 + 推荐 + 代价让用户选；发现有更简单方案就主动提，不闷头按用户原话做（push back when warranted）。彻底不清楚时三步走：**停 → 显式指出哪一段不清楚 → 问需要什么信息才能继续**，不靠猜继续。

## B. 编码中 | While Coding

- **命名简洁且语义准确**（concise and semantic naming）：文件夹、文件名、变量、方法、class 名都要短而准。避免堆砌词（`UserManagerHelperServiceImpl`）、避免无效前后缀（`xxxUtilHelper`）、避免重复语义。
- **清理自己产生的孤儿**：本次改动若让某段代码 / 导入 / 变量 / 函数 / 类型失去引用，必须同步删除。不留自己制造的 dead code / no-op config。
- **不主动清理预先存在的死代码**：发现历史遗留的死代码、注释掉的旧实现、可疑空配置、「可能以后用」的分支时，**提示用户但不顺手删**，除非用户明确要求。越界清理比保留遗留风险更大。
- **注释「必要且够用」**：
  - 方法默认写注释（极简单的赋值/转发可豁免）。
  - 重点说**为什么这样做**、边界/约束、关键变量含义、必要分支理由。不写翻译式注释（"increment i by 1"）、不写显而易见的逐行注释。
  - 方法注释优先各语言原生文档注释规范（docstring / JSDoc / Javadoc / godoc / rustdoc 等）；整体优先块级注释；避免空洞注释。
- **类型定义统一收敛**：同业务模块的类型 / schema 集中收敛到统一位置（如 `type.ts` / `types/` / `schema/` / package 内 `model.go` 等），调用方复用而非各处重定义。
- **不做类型 / 泛型炫技**：类型与泛型保持精简、可读；不为了表达力写难懂的条件类型、深层映射、复杂泛型签名、过度 trait bound。可读性 > 表达力。
- **不用 flag/mode 切换业务流程**（no mode dispatch）：禁用 `bool` / `enum` / 字符串 `mode` / options bag 在同一函数 / 同一接口里切换本质不同的业务行为。判断标准：**调用方是否需要先知道内部模式才能正确调用？参数组合是否越来越多导致行为难以预测？** 是就拆成多个独立操作，由正确的抽象各自承载。允许：简单配置项、外部库参数、无状态格式化选项（如 `{ hour12: false }`）。

## C. 变更安全 | Change Safety

- **默认只做局部修改**：读取、搜索、列目录、看 diff、改现有文件、跑最小验证。不做全量格式化、全量重排、大范围批量替换。
- **能改现有文件就不新增文件**；确需新增时优先放入现有合适目录，不在仓库根目录直接新增（包括 log、临时脚本、调试输出、一次性说明文档）。
- **未经明确要求不重命名 / 不移动 / 不调整目录层级**。
- **不修无关问题**（out of scope）：发现可以提示给用户，但不顺手扩改。
- **存量报错与当前任务无关**：仓库已有的全局静态检查 / 类型检查 / lint / 测试存量报错一律视为范围外，不处理也不作为收尾事项。
- **不引入新依赖**：未经明确要求不新增第三方依赖（库 / 框架 / SDK / 中间件 / 工具链），不调整目录结构。
- **禁兼容旧逻辑**（no legacy compatibility）：除非用户明确要求，不兼容旧字段 / 历史分支 / 双轨口径；不写去重 / 判空 / 重组映射等修正逻辑兜底已删除的旧字段。
- **不为不可能场景做防御**（no defensive code for impossible cases）：不在已被框架 / 类型系统 / 上游契约保证的位置加 null check、try-catch、fallback、兜底分支；输入校验只在系统边界（用户输入、外部 API、跨服务调用）做，可信内部调用边界默认信任。

## D. 敏感操作 | Sensitive Operations

- **`.env*` / 密钥 / 证书默认只读**。确需修改要用户明确要求，且交付时说明原因与影响范围。
- **禁破坏性命令**（destructive commands）：
  - `rm -rf`、`Remove-Item -Recurse -Force`、`del /s /q`
  - `git clean -fd`、`git reset --hard`、`git checkout .`、`git restore .`
  - 任何「清空目录」「批量覆盖」「回滚历史」类操作
  - 上述操作必须经用户明确确认后才能执行。
- **不主动删除文件或目录**。
- **提交前查敏感信息**：任何 commit / push 前自查是否含密钥、令牌、凭证、内部敏感地址、生产数据库连接串等。发现就停止，先与用户确认。
- 工具能力前置确认 / 浏览器无痕等元层约束见 `$oms-meta` 第 3 条。

## E. 验证策略 | Validation Strategy

（**默认局部验证**：只做改动涉及的文件夹 / 单文件验证，不做全量校验；仅当用户明确要求才执行全局 type-check / build / 全量 lint / 全量 test。下列为具体细则。）

- **先定成功标准再实现**（goal-first execution）：开干前明确「本次完成的可验证标志是什么」，再写代码。
  - 「添加校验」→ 先写一组无效输入样例 / 测试，再让它通过
  - 「修复 bug」→ 先写能重现 bug 的样例 / 测试，再让它通过
  - 「重构 X」→ 重构前后行为对齐（已有测试 / 关键路径样例都通过）
- **多步骤任务先列计划再做**：超过 2 步的任务，先输出「步骤 → 验证」清单，每步完成跑对应验证再进下一步；中途若偏离立刻回到清单。
- **不跑生产构建作为验证**：生产构建 / 打包 / 发布命令默认不执行（如各语言生态的 `build` / `package` / `release` / `bundle` / `publish`）。优先选择类型检查、lint、单测、局部走查这类更快的校验方式。确需构建时先说明原因征得同意。
- **接口/数据流改动核对链路**：改了接口参数、字段映射、数据流时，至少核对一次「上游入参 → 接口契约 → 下游消费」三段链路是否对齐（具体链路形态由领域 skill 定义）。
- **类型检查、lint、已有测试是否跑，按任务影响范围独立判断**。一行注释改动跑全量类型检查是过度。
- **替代验证**（fallback verification）：无法跑自动化验证时（环境缺失、需要真机、需要后端联调），说明替代方案（代码走查、关键断言、人工验证步骤说明）。
- **测试服务真实行为，不维护旧实现细节**（tests track behavior, not implementation）：发现已有测试在验证旧实现细节且与当前设计冲突，应重写或删除；测试若仍表达有效业务行为，应优先更新而非删除。**不为让旧测试通过保留错误设计 / 兼容废弃逻辑**。

## F. 交付前自查 | Self-Check Before Handoff

报告前用以下问题对照自己的 diff，任一项失败就回头修正：

- **复杂度自检**：资深工程师看到这个 diff 会不会觉得「明明能少一半代码」？会，就重写更简洁版。
- **每行可追溯**：每一行修改都能直接对应到用户请求 / 本次任务的某个目标。无法对应（顺手优化、顺手重排、顺手注释美化）就删掉。
- **孤儿已清 / 遗留未动**：本次改动产生的孤儿代码已删，预先存在的死代码未碰（见 B 节）。
- **成功标准已达成**：E 节定义的可验证标志已经实际跑通（而不是「按理应该通过」）。

## G. 停止信号 | Red Flags for Redesign

实施过程中**任意时刻**出现以下信号，立即停止硬推，回到设计层重新审视边界 / 抽象 / 归属，而不是继续打补丁。任一信号触发就向用户说明并提议重设计：

- **改动扩散到很多文件**——多半归属错误或抽象边界错位。
- **同一知识 / 校验 / 映射在多处重复**——边界没切对。
- **命名变得困难**（找不到准确的名字）——抽象本身有问题。
- **需要用注释解释一个别扭的接口**——接口形态有问题。
- **为特殊情况不断增加 flag / mode / switch**——一个操作塞了多套业务流程（见 B 节）。
- **为兼容旧逻辑保留大量死旧代码**——重构没做彻底（见 B/C 节）。
- **修复方案看起来像绕过问题而不是根治**——选错路径，回到 root cause。
- **新增的抽象 / 接口 / 配置让当前问题更难理解**——抽象付不起成本，撤销。

## H. 交付报告 | Handoff Report

交付时报告必须包含：

1. **改动文件**：列出所有新增/修改/删除的文件，**用绝对路径或仓库相对路径**，不写「我改了几个文件」这种模糊表述。
2. **核心原因**：每组改动一句话说明「为什么这样改」（不是「改了什么」——文件 diff 已经说明改了什么）。
3. **验证方式**：说清楚跑了什么命令、看到什么输出。没做自动化验证时说明替代方案。
4. **未做的事**：明确列出本次没做、留给用户或后续任务的事项。避免用户后来发现「以为做了其实没做」。
5. **风险与边界**：改动可能影响的相邻模块、需要用户复测的场景、已知的限制。

## 反 anti-patterns

- ❌ 写新工具函数前不搜项目内已有的 utility 目录（`src/utils/` / `pkg/util/` / `internal/util/` 等）看有没有现成的。
- ❌ 改个 bug 顺手「重构」无关的 3 个文件。
- ❌ 需求歧义时默默挑一种解释埋头实现，不向用户呈现多种解释 + 推荐。
- ❌ 顺手清理预先存在的历史死代码 / 注释掉的旧实现，不区分「自己产生的孤儿」与「遗留」。
- ❌ 在永远不会为 null / 永远不抛错 / 已被类型系统或上游契约保证的位置加防御性 null check、try-catch、fallback 兜底。
- ❌ 用 `bool` / `enum` / 字符串 `mode` / options bag 让一个函数承担多种本质不同的业务操作（如 `mode = "create" | "update" | "delete"`），调用方需要知道内部模式才能正确调用。
- ❌ 改测试时为了让已与当前设计冲突的旧测试通过，反过来保留废弃逻辑 / 兼容代码。
- ❌ 在仓库根目录新增临时脚本 / 日志 / 笔记（如 `test.js` / `tmp.go` / `debug.log` / `notes.txt`）。
- ❌ 改了一个字段映射就跑生产构建命令（`build` / `package` / `release` 等）做验证。
- ❌ 没定成功标准就开干（「先写写看」），交付时说不清「完成」的判定依据。
- ❌ 交付时只说「完成了」，不列改了哪些文件、跑了什么验证。
- ❌ 看到 `.env` 里有占位符就主动改成真实值。
- ❌ 为「未来可能的需求」预先加一个抽象层。
- ❌ 为兼容已删除的旧字段保留判空 / 兜底逻辑。
