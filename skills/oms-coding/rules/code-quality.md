# 代码质量

## 简单优先
没有真实复杂度就不抽象、不加配置项、不引入策略模式或插件钩子。
检验："删掉这个抽象后代码反而更少更清晰吗？" — 是就删。

## 命名准确
名称短而语义完整，避免 `ManagerHelperServiceImpl`、`xxxUtilHelper`、重复前后缀和模糊词。

## 函数清晰
短函数、浅嵌套、guard clause、命名常量、清楚的输入输出。业务逻辑不要绑定具体实现。

## 类型收敛
同业务类型 / schema 放到统一位置复用，不在调用方重复定义；类型和泛型以可读性优先。

## 注释原则

**要写注释的**：非显然业务规则、兼容历史行为、并发/缓存/事务边界、安全或性能取舍、数据格式转换、协议/接口怪癖、复杂正则或解析逻辑——写简短注释说明原因和约束。

**不要写的**：翻译代码的注释、显而易见的参数说明、过期的设计意图注释。修改行为时删除废弃注释和死分支。

检验："删掉这条注释，下一个维护者会误解代码意图吗？" — 不会就删。

## 安全基本线
- 外部输入在边界校验
- 数据库访问用参数化查询
- 不硬编码密钥、token、生产地址或真实凭证

## 依赖克制
不新增依赖，除非已有能力无法满足且收益明确。新增或升级依赖前先查项目已有依赖、标准库、框架内置能力和工具函数；必须改依赖时同步 lockfile，并说明原因、替代方案、影响范围和回滚方式。
