# 通用审查规范 | Review Guidelines

本 skill 管“如何审查代码、diff、PR、方案和实现”。代码修改纪律见 `$oms-coding`，事实核验和工具边界见 `$oms-meta`，问答风格见 `$oms-qa`。

## 1. 审查前先核事实

- 先阅读需求、相关 diff、调用方、测试和项目既有约定；不要只凭片段下结论。
- 先判断变更类型（功能 / 修复 / 重构 / 安全补丁）和影响范围；留意是否夹带与目标无关的改动（scope creep）。
- 每个问题必须能指向具体文件、代码位置、契约、测试或可复现场景。
- 涉及库/API 行为、框架约束、浏览器/数据库差异时，能查文档或本地代码就先查。
- 不把个人偏好当缺陷；风格问题只有违反项目约定或影响维护时才列出。

## 2. 风险分级

使用这四级，避免夸大：

- **Blocker**：会导致数据损坏、安全漏洞、线上不可用、破坏公开契约，必须先修。
- **Major**：明显 bug、竞态、权限绕过、错误处理缺失、测试会失败，建议本次修。
- **Minor**：可维护性、边界体验、局部重复、命名或测试覆盖不足，可排期修。
- **Nit**：纯风格或微小一致性建议，不能阻塞合并。

每条问题写清：级别、位置、原因、影响、建议修法；能给最小修复方案就给。

## 3. 审查重点

通用：

- 是否满足用户需求和验收标准；是否改了无关行为。
- 是否破坏 API、数据结构、错误格式、状态码、权限、路由、样式或交互等既有契约。
- 是否存在静默兜底、吞错误、假成功、过度兼容、mode 堆砌、无意义防御。
- 是否复用了项目既有组件、工具函数、类型、schema、middleware、请求封装和测试模式。
- 是否有生成文件、lockfile、snapshot、migration、API client 等改动；这些改动是否能追溯到源变更。
- 是否有调试代码、临时文件、真实凭证、无关格式化、行尾或权限噪音。

安全（逐项排查，不止笼统说“注意边界”；逐项对照与 ❌/✅ 示例见 `references/security-review.md`）：

- 注入面：SQL / 命令 / 路径穿越 / 模板 / 不安全反序列化，以及用户输入直接拼进敏感操作。
- 认证授权：鉴权缺失、越权访问、权限判断绕过、会话与 CSRF 防护。
- 敏感数据：硬编码密钥 / 凭证、日志或错误信息泄露、加密与传输不足、配置文件暴露。
- 可信边界：外部输入、并发、异步任务、数据库事务、网络请求是否做了对应校验与隔离。

性能与资源（修法示例见 `references/performance-review.md`；先有瓶颈证据再提级）：

- 算法复杂度劣化、循环内重复计算、数据结构选型不当、缺少缓存/记忆化。
- 数据库 N+1、缺索引、`SELECT *`、低效 JOIN。
- 资源泄漏：未关闭的句柄 / 连接、内存泄漏、协程 / 线程 / 连接池耗尽。
- 网络调用：同步阻塞、缺超时与重试、缺连接池、重复或过量请求。

测试质量：

- 测试是否断言了有意义的行为，而非只跑通不校验（避免覆盖率假象）。
- 是否绑死旧实现细节，导致行为没变却被迫改测试。
- 错误路径、边界条件、并发场景、bug 回归用例是否覆盖。

兼容与迁移：

- 破坏性变更是否有迁移路径、废弃告警、版本策略；调用方 / 客户端是否同步。
- 数据迁移是否可回滚、有兼容窗口；改字段 / 状态 / 错误码是否影响历史数据和老客户端。

依赖与供应链：

- 新增依赖是否必要、是否已有能力可复用；是否引入已知漏洞或不兼容 license。
- lockfile、生成的 API client、schema 产物是否与源改动一致、可追溯。

文档与记录：

- 公开 API、破坏性变更、配置变更是否同步文档 / changelog / 迁移指南。
- 是否残留过期注释、无 ticket 的 TODO/FIXME、被注释掉的死代码。

## 4. 输出格式

默认先给结论，再列问题：

```text
结论：<可合并 / 需先修 Blocker / 建议修 Major 后合并 / 信息不足>

发现：
1. [Major] path/to/file.ts:42 — <问题标题>
   影响：<会发生什么>
   建议：<最小修法>

未发现 Blocker。
验证：<已查看的文件/命令/测试；未验证的说明>
```

如果没有实质问题，明确说“未发现需要阻塞的缺陷”，不要为了显得有价值而硬挑 nit。

## 5. 审查边界

- 不擅自修改代码；用户要求“review”默认只审查并给建议。
- 需要运行重型测试、联网、构建、发布或访问外部系统时，先说明原因并按平台审批规则执行。
- 不能验证时说明缺失信息和剩余风险，不输出假确定结论。
- 对 AI reviewer / 子代理结果要二次核验；常见误报包括信任边界混淆、忽略设计注释、变量来源读错、把测试实现细节当行为缺陷。

## 6. 参考清单

正文给判据，细化的 ❌/✅ 对照和逐项勾选在 `references/` 下，按需加载（不支持自动加载的工具可手动打开）：

- `references/security-review.md` — 安全审查：注入 / 认证授权 / 敏感数据 / SSRF / XXE / CORS 的 ❌/✅ 对照。
- `references/performance-review.md` — 性能审查：复杂度 / N+1 / 资源泄漏 / 网络调用 / 缓存的 ❌/✅ 对照。
- `references/review-checklist.md` — 完整 review checklist：覆盖 §3 全部维度的逐项勾选模板。

reference 沿用本 skill §2 的 Blocker/Major/Minor/Nit 分级；其中的阈值仅作参考，不当硬性门槛。

## 反 anti-patterns

- ❌ 没读调用链就说“这里可能有问题”。
- ❌ 把所有建议都标成严重问题。
- ❌ 用“建议优化一下”代替具体影响和修法。
- ❌ 为了凑数量列出无关 nit。
- ❌ 没验证就声称测试通过或风险已排除。
