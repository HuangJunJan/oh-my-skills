# 输出格式与审查边界

## 默认输出格式

先给结论，再列问题：

```text
结论：<可合并 / 需先修 Blocker / 建议修 Major 后合并 / 信息不足>

发现：
1. [Major] path/to/file.ts:42 — <问题标题>
   影响：<会发生什么>
   建议：<最小修法>

未发现 Blocker。
验证：<已查看的文件/命令/测试；未验证的说明>
```

如果没有实质问题，明确说"未发现需要阻塞的缺陷"，不为了显得有价值而硬挑 nit。

## 审查边界

- 不擅自修改代码；用户要求"review"默认只审查并给建议。
- 需要运行重型测试、联网、构建、发布或访问外部系统时，先说明原因并按平台审批规则执行。
- 不能验证时说明缺失信息和剩余风险，不输出假确定结论。
- 对 AI reviewer / 子代理结果要二次核验；常见误报包括信任边界混淆、忽略设计注释、变量来源读错、把测试实现细节当行为缺陷。
