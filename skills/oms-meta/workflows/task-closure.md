# Task Closure Protocol (AAR)

本 workflow 定义了"任务完成"的真正含义——不只是跑通代码。
所有非琐碎任务结束前必须经过这一步。

## Task Anchor（任务锚点）

**Goal:** 扫描任务中产生的新模式、新陷阱、缺失规则、过时规则，通过 2/3 阈值后录入对应位置。

**Boundaries:**
- 不录入一次性变通方案
- 不录入看代码就能明白的事情
- 不录入轻微的风格偏好
- 不录入官方文档已充分覆盖的内容

**Done When:**
- 4 个 AAR 问题全部扫完
- 所有"是"的项通过了 2/3 阈值
- 录入内容已泛化，脱离当前项目上下文也能看懂
- 录入位置正确（rules / references / workflows）

---

## 触发条件

任何任务声明"完成"之前，除非属于以下跳过条件：
- 纯格式化（只改空格/换行/缩进）
- 纯注释（只增删注释，不改逻辑）
- 纯依赖版本变更（只改版本号，无行为变化）

### Rationalizations to Reject（借口拦截表）

以下借口来自真实失败，禁止凭空扩充。Agent 发现自己产生类似想法时立即停下：

| 借口 | 为什么是假的 | 正确做法 |
|------|------------|----------|
| "这次改动太小了，AAR 没必要" | 小改动也可能引入新模式/新陷阱 | 30 秒扫描不挑大小 |
| "这个 gotcha 已经记在 references 里了，不用再更新 workflow" | 记了但任务路径上读不到 = 没记 | 已激活才算录入 |
| "我先把 main 逻辑写完，AAR 后面补" | 永远是"后面补" = 永远不补 | 完成前必须走 AAR |
| "这次只是格式化/注释，不算任务" | 格式化也可能改坏逻辑 | 按跳过条件严格判断 |
| "这个规则我知道，不用重读" | 上下文压缩后规则已不在上下文 | 必须重读对应文件 |
| "先把桥搭起来，后面再清理" | 遗留的孤儿代码永不被清理 | 本次产生的孤儿本次清理 |

## 30 秒 AAR 扫描

在确认主体工作完成并验证后，逐项过：

- [ ] **新模式？** — 用了未记录的模式或约定吗？
- [ ] **新陷阱？** — 遇到了不提前知道就会浪费大量时间的问题吗？
- [ ] **缺失规则？** — 因为缺少某条规则导致走了弯路吗？
- [ ] **过时规则？** — 发现现有规则已经不准确或不再适用吗？

全部"否" → 任务结束。

任何一个"是" → 进入录入流程。

## 录入流程

### 2/3 阈值

新发现通过至少 2/3 才录入：

1. **可重复？** — 别的任务也会遇到同样的场景吗？
2. **代价高？** — 踩中会导致 30 分钟以上的调试或错误吗？
3. **代码不可见？** — 从代码/文档中无法直接看出这个陷阱吗？

### 泛化规则

记录内容必须脱离当前项目上下文也能看懂：

- ❌ "修复了 UserService 里的 filter 注册顺序问题"
- ✅ "Filter 必须在 app init 之前注册，否则首次渲染空白——框架规则见官方文档 §Lifecycle"

### 录入位置

- 稳定约束 / 通用原则 → `rules/`
- 陷阱、架构笔记、生命周期坑 → `references/gotchas.md`
- 有序步骤 / 完成检查清单 → `workflows/`
- 会话历史 / 调试过程 → **不写进 skill**（用 git / CHANGELOG）
